# Design principles

This page states the rules the extension's code relies on. Code comments point here by section name. If a change would break one of these rules, discuss it in an issue before you write the code.

The extension explains Dynamics 365 model-driven forms in context. It runs in two modes from one codebase:

- **Lite:** no backend. It reads Dataverse metadata as the signed-in user.
- **Connected:** the user enters their organization's Pathix™ address and signs in. Cards then show what Pathix found in its scans.

Pathix is not affiliated with Microsoft.

The extension acts only on Dynamics 365 org hosts (`*.crm*.dynamics.com`: `<org>.crm.dynamics.com` or `<org>.crm<N>.dynamics.com`). The manifest's content scripts match every `https://*.dynamics.com/*` page, so both scripts check the host first (`src/bridge/org-host.ts`) and, anywhere else, set no global, add no listener, post no message and start no timer; `test/org-host.test.ts` runs both bundles on refused hosts to hold this. GCC High, DoD and China are not supported yet.

## Entry points

Every feature is reachable with the mouse. The toolbar popup is the primary way in; keyboard shortcuts are accelerators for people who learn them, and no feature depends on one.

- **Keyboard shortcuts are manifest commands**, never key handlers on the page. The browser owns the keys: it lists them at `edge://extensions/shortcuts` (`chrome://extensions/shortcuts` in Chrome), the user can rebind or clear any of them, and a page never sees a key a command claimed. A capture-phase keydown handler on every Dynamics page collided with browser features (Edge's Alt+Shift+S is Visual Search), so the content script listens for no shortcut key at all; `test/toolbar.test.ts` scans `src/content` for modifier checks. Escape still closes an open panel or card: that is the panel's own key, not a shortcut. The manifest declares `_execute_action` (opens the popup) and one command per feature (`src/runtime/commands.ts`). The service worker's `chrome.commands.onCommand` sends the tab the same content command the popup sends.
- **One default key.** A command's key is taken in every tab, not only on Dynamics pages, and a letter with Alt (AltGr on some layouts) or Option on a Mac can type a character. So the extension sets one default shortcut, for the popup, and every feature's shortcut is opt-in at the browser's shortcuts page. The popup's key is on one line of the manifest, with an explicit `mac` key that uses Control (`MacCtrl`) rather than Option. The browser does not assign a suggested key that is already taken, so the popup always shows each command's current key from `chrome.commands.getAll()`, or "No shortcut", with a link to the browser's shortcuts page.

- **The toolbar popup** (`src/popup`, the manifest's `action.default_popup`) opens when the toolbar icon is clicked. Top to bottom: the active tab's connection state, in the words the cards and the badge already use; **This form**, with an X-ray switch and the Event map, What changed, Save preview and "Card for the selected field" buttons, each showing its shortcut; the admin center overlay switch, which shares `src/options/admin-toggle.ts` with the options page, so its permission request still runs from the user's click; and links to the options page and the demo. The permission prompt can close the popup before it stores the setting, so the click first records the intent (a timestamp, not awaited, so the gesture holds) and the worker's `permissions.onAdded` finishes turning the overlay on when the intent is under a minute old (`completeEnableIntent`). A denied prompt seen by the popup clears it, and so does turning the overlay off. What remains: a deny or dismissal that closed the popup reaches no one, so within that minute, a grant of the admin host by another route (the browser's site access settings) would turn the overlay on.
- **How it reaches the form.** The popup finds the active tab with `chrome.tabs.query({ active: true, currentWindow: true })`, which needs no permission for the id. If the browser gives the tab's address, the popup reads its host only, to tell a Dynamics page whose content script is gone (the extension was reloaded under it: "Reload this page") from any other page, and keeps nothing. Without the `tabs` permission, which the extension does not ask for, Chromium gives no address even for the content-script hosts (measured 2026-10-09), so in practice a tab that does not answer gets one line covering both: "Open a Dynamics 365 record form to use these. If one is open, reload the page. US Government (GCC High and DoD) and China clouds are not supported yet." The last sentence is there because a tab on those clouds never answers either. It asks the tab's content script two questions, each checked on arrival. `formState` (is a record form open, is X-ray on) is answered at once from the content script's own state. `connectionStatus` can wait on Pathix. It is asked only after `formState` answered, which proves the content script is alive, so one timer decides: silence past it is Pathix's ("did not answer in time"), a failed send or a malformed answer is the extension's. The connection line says "Checking Pathix…" until then, and a slow or failed Pathix never disables the form's actions. The mode is not asked of the tab: the popup reads it fresh from storage each time it opens, so adding or removing a Pathix address shows without a tab reload. The popup keeps the latest known state, so a switch turned while Pathix is checked keeps its position when the answer arrives. The logic is `src/popup/session.ts`, tested with fake browser calls; `popup.ts` only supplies the browser and draws. Each button sends a typed command (`openEventMap`, `openWhatChanged`, `openSavePreview`, `openFieldCard`, `setXray`); a keyboard command sends the same kinds, plus `toggleXray`. The content script answers `openFieldCard` with whether a field had focus, and when none did the popup stays open and says so. The content script routes each to a controller's public entry point: `open()` for a panel, `toggle()` or `setOn()` for X-ray, `openFocused()` for the card of the field that has focus or last had it. A button or a command opens its panel and never closes an open one; Escape and the close button call `close()`.
- **No form, no action.** On a tab with no content script, or a D365 page with no record form, the form controls stay visible and turned off, and one line says to open a record form. X-ray and Save preview are Pathix's answers, so in Lite both are turned off with the same reason in words ("Uses your organization's Pathix") and one line pointing to Options. No upgrade button: the existing Options link is the way there. An X-ray already on can still be turned off.
- **No on-page launcher.** The extension draws nothing on a form to open its features. The hover card opens from a field's label, as before.
- **The card from the keyboard.** A card opened on purpose (the popup's button, the `open-field-card` command, or an X-ray line) moves focus to its title on its first draw, and is a dialog named by that title. Later draws of the same field (loaded, the live reads) update the card in place around the title, so focus stays and a screen reader does not announce the dialog again; while it loads, the card is `aria-busy`. Escape or its close button closes it and gives focus back to where it was: the field, or the X-ray line as X-ray last drew it, and when D365 has replaced that node, the field's first control that really takes focus (not one out of the tab order, disabled, hidden or not drawn), on this form only; with none, focus is left alone. A card that closes because the form went away gives focus to no field. While focus is inside a card opened on purpose, or one a key moved focus into, the pointer neither closes it nor opens another card. A card opened by hover never takes focus, still closes when the pointer leaves it, and gives focus to no field when a mouse user had clicked into it. The loading message, not the dialog, is `aria-busy`. Drawn again with focus inside, the event map, what changed and save preview panels put it on their heading. The popup's button says when no field is selected, and when the selected field has no card on this form. The card's host sits inside `body`, in a closed shadow root, so assistive technology reaches it with the page.

The popup adds no permission. With a popup set, `chrome.action.onClicked` never fires, so the service worker has no click handler; the demo opens from the popup's link on any page.

## Names, never values

Code that runs in the Dynamics 365 page reads logical names only: the table, the column, the control, the form id and the organization id. Four states cross as lists of those names or as fixed words: which columns have unsaved edits, which controls the form shows read-only, which columns the form submits on every save (their submit mode, never their value), and whether a save would create or update (the form's type, as the word "create" or "update"). It never reads a field value, an edit, the record id, or the page URL beyond its host. Nothing else crosses the bridge from the page to the extension.

**Quick views.** A quick view shows another record's form, read-only, inside this one. Its fields are another table's columns, so the snapshot keeps them apart from the form's own: `quickViewColumns` lists each bound inner control with its column and the quick view's table. The page reads them through `ui.quickForms` and the quick view's `getControl()`, names only, and the table through the inner attribute's `getParent()`, asked only for its logical name. Captured live: the inner control's own name is the bare column (`emailaddress1`), and the field's `data-id` is the quick view's name, a dot and that name (`contactquickform.emailaddress1-FieldSectionItemContainer`). So the dotted name is the key, on both sides of the bridge. The inner name alone is never used, since it can equal one of the form's own controls (Account's `telephone1` and the contact quick view's `telephone1`). An inner field whose table cannot be read is left out, since a card on the wrong table is worse than none. Until the quick view loads, `getControl()` answers null and the list is empty. Hovering a quick view field opens the card for the quick view's table and column in either mode, with one line saying the field is shown read-only from the related record. It carries none of the form's own context: no form id, no unsaved edits, and no "Why can't I edit" checklist, since the reason is already known. The label-form rule (form-scope.ts) does not apply to it: its card does not depend on which form hosts the quick view.

The content script reads no text out of a D365 node. X-ray v2 finds a field's label by its id and its line's place by the computed layout of the label's ancestors, never by what any node says. `test/xray-line.test.ts` pins this by scanning every file under `src/content`. (X-ray once compared the node after a label with the column's logical name, to find Level Up's chip; the line now has its own row under the field, so that read is gone.)

The page names the form, but anything on the page can post a snapshot. So the content script relays a snapshot with its own `location.host` written over the host the page posted (the only part of the address it reads besides the origin), and the service worker answers a form request only when its host is the sender's own. A Pathix environment matched on the page's organization id must also be on that host; otherwise there is no matching environment, never another environment's answers. An environment Pathix stores no usable URL for is not matched on the organization id alone, since any script on the page can name one: the card says Pathix lists the organization without an address, which the administrator can check, never that Pathix has no such environment. The card then says Pathix knows the organization under a different address, names the host of the URL Pathix stores (Pathix's metadata, never the page's), and says the environment's address may have changed since it was added to Pathix, which the administrator can check. Pathix does not let an environment's URL be edited, so the card does not ask for that. One tab may ask about three organization ids until it loads a new page, so random ids cannot drive unbounded Pathix reads. The admin center has no Dynamics host, so there the organization id alone decides.

This holds in both modes, and it is the extension's main privacy promise. Three fitness tests fail the build if it breaks:

- `test/messages.test.ts`: the bridge validator rejects any key it does not know, and any string not shaped like a logical name or a GUID. A value cannot ride along by accident.
- `test/form-snapshot.test.ts`: a fake `Xrm` full of values produces a snapshot that contains none of them.
- `test/page-source.test.ts`: page-side code must not call a value-reading `Xrm` API, read a DOM value or text, read the full URL, or open a network connection. It may call only a closed list of `Xrm` getters, each of which reads a name or a setting. It scans every file the page, content and admin center bundles are built from, following their imports, and bans each way of reaching the address (the location as text, `document.URL`, the referrer, navigation entries, the history state) except the location properties each script may read.

When you add a page-side read, extend these tests in the same change. Never weaken them. If a feature really needs a value-reading call, that is a design discussion first, never an allowlist edit.

The same rule applies beyond the page. Lite reads Dataverse metadata tables and functions only: never business records, audit data or plugin-trace logs. Its client's allowlist pins the tables, the columns each one may select (exactly the ones Lite reads, so not a step's unsecure configuration or a workflow's definition), the query options, and the shape of every filter it writes (a filter of any other shape, such as one testing a column Lite does not select, is refused). Connected mode reads Pathix, which is metadata-only too. The extension sends no telemetry. It talks only to the user's own Dataverse, their organization's Pathix and Microsoft Entra.

## Confidence vocabulary

Every writer Pathix reports carries a confidence tier. It says how Pathix knows that the component writes the column:

- **Declared:** the platform's own structure pins the column. For example, a form binds it, or a classic workflow's update step names it.
- **Parsed:** Pathix resolved the exact column by reading the component's logic: plugin code, scripts or flow definitions.
- **AiDerived:** an AI reading of the component's decompiled code or source, with the evidence attached. It is shown with its own marker and labeled "unverified". It never replaces or overrides a Declared or Parsed answer.
- **Unresolved:** Pathix saw a write but could not resolve which column it targets, for example a late-bound or dynamic write.

The card shows Declared and Parsed together as "deterministic". AiDerived always looks different from them, so a reader never mistakes an AI reading for a parsed fact. Any other tier value from Pathix shows under its own name and is never promoted to deterministic.

## Capability is not a dependency

Two questions stay separate on every card:

- **What does write this field?** Components whose logic or structure writes the column. These are the writers.
- **Who can change this field?** Principals whose security roles grant Create or Write on the table, and column security on the column.

Capability never counts as a writer, and a writer never implies capability. The card shows who can change a field apart from its writers, behind the card's "?".

## Absence is not evidence

A missing answer is unknown, never zero. When a scan is missing, a request fails, an answer is forbidden or a detector did not run, the card shows "?" or says what it cannot see. It never shows "0" or "nothing found" in place of an answer it did not get. A request that does not answer in time is a failed one: every Pathix and Dataverse request, and the redemption of a sign-in code at Entra, is aborted after 15 seconds, and the card says "Pathix did not answer in time" or "Dataverse did not answer in time". No cache keeps that failure, so the next read asks again.

A list can also come back short without failing. Classic workflows and business rules are owned by users, and teams and roles by business units. A user whose security role reads them below Organization depth gets HTTP 200 with only the rows they can see. Lite asks Dataverse for that depth (`RetrieveUserSetOfPrivilegesByNames` with `prvReadWorkflow`, `prvReadTeam` and `prvReadRole`, as the signed-in user). Below Organization, with a record filter, or when it cannot tell, the list is possibly incomplete: a count reads "at least", a ✓ or ✗ drawn from the list is ?, and "nothing is registered" becomes "of what Lite could read". A grant it did find still stands. Plugin step registrations, forms and column security profiles are owned by the organization, so they are not affected. The connected checklist's live team lines follow the same rule.

Teams and roles are narrower than that. The user's own roles are never listed: their Write depth comes from the same function, which no Read depth filters. A team's roles are the copies in the team's own business unit, so the roles of the teams Lite lists are all visible when the user reads roles at Organization depth. At Business Unit or Parent: Child depth it depends on where that depth is anchored. If the function's answer holds only the user's own roles, it is anchored at the user's business unit, and a team in that unit (the team's `_businessunitid_value` against WhoAmI's `BusinessUnitId`) is reached, a team in another unit at Business Unit depth is not, and one at Parent: Child depth might sit below the user's, which Lite does not read. If the answer also counts the roles a user holds through teams, a Business Unit row may be anchored at a team's unit, and if it does, a team Lite cannot see cannot hide a Write grant from the user's own answer anyway. Nobody has verified which holds, so `PRIVILEGE_SET_INCLUDES_TEAM_ROLES` in `src/lite/visibility.ts` is "unknown", names the live check that settles it, and below Organization depth every team's roles are unknown until it is set. What User (Basic) depth reaches on a table owned by business units is not verified, so Lite does not rely on it. A user in no team has nothing hidden there. The teams themselves are another matter: a user can be in a team of any business unit, and below Organization depth on reading teams such a team may not be listed, which Lite cannot detect, so that case is hedged whenever it applies. Column security reads only the teams, so its hedge names teams alone.

Organization depth on the table's own Write privilege also counts as every record only with no record filter: an empty `RecordFilterId` or the empty GUID. Any other value means the grant covers the records a filter selects, and an answer with no `RecordFilterId` at all is unknown. The same rule applies to the read depths above. A team role's depth comes from `roleprivilegescollection`, which carries no filter, so a team's Organization depth counts as every record only when the table's definition says the Write privilege cannot take a record filter (`CanBeRecordFilter` false); otherwise the line says a record filter may narrow it.

Pathix's own empty answers follow the same rule. `/scans?environmentId=` lists only an environment's 100 latest scans, with no status filter, so a full list with no Completed scan means the latest Completed scan is unknown, never that there is none: Pathix may still answer from an older one. `/findings/open-counts` leaves out a column its latest scan does not hold, and a null `readiness` means there is no Completed scan: either one is unknown (a `readiness` key that is absent is a Pathix older than it: a positive count still shows, but a zero is unknown, since a measured zero cannot be told from a sweep that has not run), never "no open findings". A current Pathix's `/findings/field-writers` and `/findings/field-dependents` refuse a column the latest scan does not hold with Pathix's typed 404 (a non-empty string body; a 404 with no body is a route miss, unknown). An older Pathix answers them with an empty list, so the card does not take an empty list on its own as zero. It reads the column as **not in Pathix's latest scan** when the writers, dependents or permissions read answers the typed 404, when the open counts leave it out while a Completed scan exists (a `readiness` object, whatever the findings sweep is doing: Pathix decides omission by the scan's columns), or when its table is in the environment's `excludedEntities`. The card then says "Not in Pathix's latest scan" and shows no counts, rows, findings or contrast line; X-ray writes `?` for every count; the brief says the column is not in the scan.

The rule also covers what Pathix cannot see at all. External integrations that write through the API leave no trace in metadata, so every card says that they are not counted.

## Live freshness

Connected mode may make one kind of live Dataverse call beyond the user's own security state: the freshness case. For a component Pathix already knows, the content script reads its change date through the same allowlisted client as Lite, and compares it with when the latest Completed scan was queued and completed. The date is `modifiedon`, except for a form: the `systemform` table has no `modifiedon` (a read that selects it answers 400), so a form's date is `publishedon`, when it was last published. An edit to a form that is not published does not show, and publishing again with no change does. Wherever the panel or a badge dates a form, it says "published", never "saved" or "modified". A newer date shows a "changed since scan" badge, labelled "live". The call is paired with a Pathix fact and never replaces one.

Three answers, never two: changed, unchanged, or unknown. A component is changed when its date is after the scan completed, and unchanged only when its read succeeded and its date is on or before the scan started. The start is when the scan was queued: `/scans` serves that time, not when the scan began running (only `/scans/{id}` has that, and the extension makes no request per scan), so the window can open early, which only widens what is unknown. A date in between is unknown, and the card says the component changed around the time of the scan, so the scan may not show it. A type with no live read, a failed or refused read, a component the answer left out, or an unreadable date is unknown, and the card says how many "could not be checked". What the call learns lives in memory for the session. It is never stored and never sent to Pathix.

The ledger view has a limit worth knowing. Pathix ties a ledger row to a table only when the row names one: a write or read of a column, a column change, column security. Since a Pathix update of 2026-10-08, a component that was added, renamed or changed in source carries its table too, from the next scan on; earlier rows are not backfilled. In a newer Pathix, a form's source version is its `publishedon`, so a form published again between two scans is a `SourceChanged` row with its table. Form rows start from the second scan after the update, since the first has no earlier date to compare. The panel labels such a row "Republished", in Lite's "published" words: an unpublished edit does not show, and publishing again with no change does. A row with no table is not returned by a table filter. The panel says so, briefly, and links to the full ledger.

An empty ledger is not "no changes" unless every scan in the window compared. In a current Pathix, `/changes` carries `windowCoverage`: how many scans completed in the window, and on how many of them changes or findings were not compared, or Pathix has no record of whether they were. The panel names each gap in its own line, and when some scans did not compare changes it says only that none of the compared scans recorded a change. With no scan in the window it says no changes were compared. An older Pathix serves no coverage, and the panel falls back to the latest scan's finding gate.

## Connected parity

Anything Lite shows, connected mode shows from Pathix. Where Pathix cannot serve it yet, the gap is closed in Pathix, not with a live call. In connected mode the card reads:

- the dependency count in the contrast line from the scan (`platformDependentCount` on the field-dependents answer). It counts the column's Dataverse dependency records, measured when Pathix scanned, so it can lag a later change, and the line says "Dataverse has N dependency records". It is usually the count in Dataverse's Show dependencies view, which Lite's "tracks N components" reads, but it can differ, because that view groups some records differently. The "?" says so. A count Pathix did not measure is unknown, never zero;
- each writer's triggers from its row: the filtering columns, "fires on every update" and a cloud flow's row-filter flag. A missing or null field is unknown, never "no filter";
- a plugin step's images from its registration. No answer is "unknown", never "no images";
- the open form's controls from the field-dependents answer, for "Why can't I edit this field?". The hovered control is matched by its id, on the form row whose Dataverse id is the open form's. A control id that is not listed is unknown. It never takes the form-level answer, which describes only the controls listed.

Connected mode calls Dataverse live only for the signed-in user's own security state (their column security profiles, through their teams too, and their own access to the table) and for the freshness check above. Each live read runs only once Pathix has answered with the card or ledger rows it pairs with: a sign-in prompt, an error or "not scanned" makes no Dataverse read, and neither does a column not in Pathix's latest scan, whose card shows no "Why can't I edit" checklist at all. The Pathix card shows as soon as Pathix answers; the checklist's live lines say "Checking" until the user's own reads come back, and after 10 seconds they say "Could not read your access in time", never a verdict. Every live line says "live". Lite and Pathix apply the same test to a control that displays another form: a quick view or a form component host is locked, whatever its disabled flag says.

## The admin center overlay

The Power Platform admin center (`admin.powerplatform.microsoft.com`) is the second place the extension runs. It is opt-in, connected-only and read-only. The same rules hold there, with these specifics:

- **Permission.** The manifest holds the admin host as an optional host permission, and has no content script for it. The options page asks for that one host from the user's click, and the service worker then registers the page script with `chrome.scripting.registerContentScripts` (the `scripting` permission exists for this and nothing else). Turning the overlay off, or the browser reporting the permission removed, unregisters the script and tells open admin tabs to remove what they drew. The worker reconciles the registration with the setting and the permission when it starts and on every permission change, whichever origins the browser names, so a revoked permission never leaves a script behind. An open options page or popup redraws its switch when a permission or the setting changes, so a host removed in the browser's own settings shows off there too. A grant made elsewhere turns nothing on. The script matches that host and no other. It never matches a sign-in host. `test/admin-overlay.test.ts` pins the manifest, the registration and the toggle.
- **What the page script reads.** The path of the address (never the query or hash), the target of role links in the role list, and the text of a grid cell only when the whole text is a GUID (an Application ID). Names, emails and every other value are dropped where they are read. It never reads the page's tokens, storage or cookies, and it makes no network call. `test/admin-page.test.ts` holds this by scanning `src/admin`: one text read, one attribute read, one place for the path, no network, no storage, no markup from strings, and only the extension's own hosts inserted or removed.
- **Where Pathix calls come from.** The page script sends ids to the service worker, which asks Pathix with the extension's own sign-in and answers with strings. The environment is matched on the Dataverse organization id in the path, the way a form is.
- **Business unit copies are folded into the root.** Dataverse keeps a copy of every role in every business unit, and Pathix lists each copy as its own row with its own holders. The admin center lists root roles, so the overlay sums the root's row and every row whose `parentRootRoleId` is the root's Dataverse id (its `sourceId`, never its Pathix `id`). Each copy belongs to one business unit, so the sum counts holders. Whether the sum is exact follows one rule, read from the whole role list:
  - a row names a parent root role: the scan carries the column, so the fold is exact, and a root with no copy has none;
  - no row names one and no two rows share a name: the environment has one business unit (with more, every role would have a same-name copy), so every count is exact;
  - no row names one but rows share a name: the scan predates the column, and which rows are copies is not known. A role's numbers then cover its own row only, and say so. On the badge the assignments read "N+ assigned" and a findings count above zero reads "N+"; in the banner the headline reads "Assigned to at least N humans and M integrations", the findings line starts "At least", and the severity is "highest seen", because a copy's finding could be higher. Inside an "at least" sentence a zero part is left out, never printed ("at least 1 human", not "at least 1 human and 0 integrations"). A holder or findings count of zero for such a role reads unknown, in the badge ("? assigned"), the banner and the tooltip alike, never a bare zero or "No open findings name this role".

  A page that opens a business unit copy's own id shows that copy's numbers and says they are for the copy only. A copy the open counts leave out makes the role's findings count a minimum ("At least", "N+"), or unknown when the rest sum to zero. A grid that reuses a row for another role or application user has its badge or chip removed or redrawn for the new id, never left showing the old one.
- **Silence is the failure mode.** A page that is not one of the three routes, no Pathix, signed out, an environment Pathix does not scan, a role not in the latest scan, or an answer that did not come all leave the admin center untouched: no banner, no error. Inside a banner, a part that failed reads "unknown", and a banner with nothing known is not drawn. The note about same-name rows is not knowledge of the role: on a scan that predates the parent column, a role with same-name rows, no holders of its own, no team and no findings of its own draws no banner. The overlay draws only where it is sure of the place: a banner needs a breadcrumb to sit under, and a chip needs a row with exactly one GUID cell. Otherwise it draws nothing.
- **What the numbers are.** Everything is from the latest Completed scan, and the banner says so with the scan date. The split by kind comes from Pathix's role list, with no request per role. "Humans" are users and "integrations" are application users, both holding the role directly and neither managed by the platform. Users the platform manages (Power Pages site users, agents, unlicensed activity parties) are their own kind, "platform-managed users", and never count as humans or integrations: Pathix decides that before the principal type. A team that holds the role is named apart, and its members are not counted: Pathix does not list them. The findings are the role's open findings: Open or Reviewing in the admin's triage, without system noise and without the finding types the admin suppressed, the same set as Pathix's findings page. The banner and the badge say "open findings", and "No open findings name this role" says what is hidden. A role the open counts leave out is not in the latest scan, and its findings read unknown, never zero.
- **Cost.** A role page makes two Pathix reads: the role list and the open counts of the role and its copies (one more per 100 copies). A role list makes the role list read (shared with the banner) and one open-counts read per 100 role ids, the listed roles and their copies, and none per row. Application users are looked up by Application ID, one read per 100 ids the page shows, so one per visible page of the grid. All of it goes through the shared response cache scoped to the latest scan.
- **Application users.** A chip says how many roles the application user holds directly. "Not in Pathix's latest scan" is said only when Pathix answered from a scan and lists the Application ID among those it looked up. An answer with no scan behind it (a null `scope`), a lookup that failed, or an Application ID two principals share draws nothing.

## Authorship comes from the publisher

Cards separate Microsoft-shipped components from the customer's own. In connected mode, the `isSystem` flag comes from Pathix, and the extension shows it as "Pathix marks it Microsoft-shipped", without saying how Pathix decides. Pathix decides it by publisher identity, with three narrow exceptions. Microsoft's `cc_` platform script bundles arrive under the customer's default publisher, so Pathix knows them by name. A model-driven app's Copilot knowledge configuration falls back to a managed row with a Microsoft-reserved app prefix. A harvested catalog of the components Microsoft creates unmanaged when it provisions an environment also marks them Microsoft-shipped. These are views, dashboards, duplicate-detection rules, a Copilot agent and attribute maps. They carry the default publisher too, so publisher identity cannot tell them from the customer's own work. The catalog only settles a component the publisher left undecided and never overrides a publisher verdict. It moves rows into the Microsoft group on both the card and the save preview. For example, a provisioned attribute map that writes a column now folds with the Microsoft writers. Because of these exceptions, copy in connected mode still does not name the signal. Lite folds by the publisher of the owning solution only, and its copy says so. A step's solution as Lite reads it is its top layer. A step created or customized in the environment sits in the Active solution, whose publisher is the default publisher whoever wrote the step, and a customized Microsoft step lands there too. Finding the base layer takes a read per step, so Lite says such a step is "in the Active layer", names no publisher for it, and never folds it.

Managed versus unmanaged is solution packaging, never authorship. Customers and their partners routinely ship their own code as managed solutions, which is Microsoft's recommended practice. So the extension never uses managed state to decide who wrote something. If Lite cannot read the publisher cheaply, it does not separate the two.

## Sign-in is confirmed by the user

Pathix's `/config` is anonymous, so any address can serve a copy of a real organization's settings. The extension therefore never signs in to an address the user has not confirmed:

- **The confirmed sign-in.** The options page shows what selecting **Sign in** trusts: the Pathix address, the tenant ID, the sign-in host and the API (the `api://...` part of the scope). Only that click starts a sign-in for settings the user has not confirmed, and only when `/config` still says what the page showed. When it succeeds, the extension stores the binding: the address, authority, tenant, client ID and scope (`signInBinding` in local storage).
- **Silent renewal names the account.** The binding also keeps the signed-in account's sign-in name, from the token's `login_hint` claim, else `preferred_username`, else `upn`. It is not part of what the user confirms. A silent request (`prompt=none`) for the binding's exact settings sends it as `login_hint`, because with several Entra accounts in the browser Entra otherwise answers "interaction required" and every hourly renewal would sign the user out. It goes nowhere but Entra's authorize endpoint. The options page's Sign in sends none, so a user with several accounts still picks one. A binding stored by an earlier build has no name and renews as before. A renewal whose token names another account (its `login_hint`, `preferred_username` or `upn`, ignoring case) is not kept: the stored token and the confirmed sign-in are removed, the reason is "Microsoft Entra answered for a different account", and nothing signs in silently again until the user selects Sign in.
- **Silent sign-in only for that binding.** Loading the options page, a card, X-ray, the badge and the admin center overlay sign in silently only when what `/config` says now equals the binding exactly. A changed tenant, sign-in host, client or scope waits for a new click, and the options page says what changed. With no binding, cards say "not signed in" and the extension asks Entra nothing.
- **Sign out sticks.** Sign out removes the token and the binding (the account name with it), clears cached statuses and badges, tells every open tab, and everything there that shows Pathix's answers asks again: X-ray (its lines come off first), an open connected card (a Lite card, and a hover card already closing, are left alone), the event map, what changed and save preview panels that last answered from Pathix (a Lite panel is left alone), and the admin center overlay, whose banners, badges and chips come off. Each then says what the connection is now, for example not signed in, and a sign-in already running when the user signed out keeps nothing. Nothing signs in again until the user selects Sign in.
- **A new address starts over.** Changing or removing the address removes the token, the binding and any refused grant, and gives back the old address's host permission.
- **Only Entra.** The authority must be exactly `https://<host>/<tenant GUID>`, with the host one of the Entra clouds' sign-in hosts (`login.microsoftonline.com`, `login.microsoftonline.us`, `login.partner.microsoftonline.cn`, `login.chinacloudapi.cn`) and the GUID the tenant `/config` names. Anything else is a registration that looks wrong, and nothing goes to it. Requests that carry the token, and the `/config` read, never follow a redirect: a redirect is a failed request.

## Lite and connected

Each mode answers a different question. Every card says which one it is answering.

| Lite (no backend) | Connected to Pathix |
|---|---|
| What is **registered** or **declared**: plugin step registrations, workflows, business rules, form definitions | What **actually writes** a field, parsed from plugin code, scripts and flows |
| Live from Dataverse, for the open table | As of the latest completed scan, across every table |
| Dataverse's own dependency tracking | Parsed writers and readers, and flagged AI-derived writers |
| The current user's own access | Every principal's effective access |
| No findings | Scans, open findings and their severity |

Text Pathix writes, such as a readers coverage warning or the notes on who can edit, is shown word for word and introduced by a line of the extension's own ("Pathix notes about this count:"). The copy rules (US English, short sentences, no em dashes) apply to the extension's own strings; Pathix's sentences are not reworded, since they can name a customer's teams and carry no code that would let the extension tell one note from another. Some of them refer to the rows of Pathix's own page.

Lite counts in platform terms: "tracked dependencies", "registered to fire", "form scripts". It never says "writers", which is a claim only Pathix can make. It never counts or lists writers, and never shows a Pathix number or result. A footer line may say what Pathix does. Entering a Pathix address on the options page moves to connected cards with no reinstall. Where Pathix answers a question better, its answer replaces Lite's.
